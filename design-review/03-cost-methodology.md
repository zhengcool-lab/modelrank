# ModelRank 设计评审 —— 成本计算器 & 评分方法论

- **评审日期**：2026-10-28（周三）
- **评审页面**：
  - 成本计算器：https://modelrank-1br.pages.dev/cost
  - 评分方法论：https://modelrank-1br.pages.dev/methodology
- **评审方式**：浏览器真实渲染截图（桌面视口）+ 前端源码走查（`apps/web/src/app/cost/page.tsx`、`apps/web/src/app/methodology/page.tsx`、`apps/web/src/app/globals.css`、`apps/web/src/lib/cost-formula.ts`）
- **问题总数**：22 个（P0 × 2 / P1 × 11 / P2 × 9）

> 严重程度：P0 = 致命，阻断核心功能或严重破坏观感；P1 = 严重，明显影响体验但不阻断；P2 = 可优化，细节打磨。

## 一、成本计算器（/cost）

### 1. **[P1] 单位体系在「万」与「M（百万）」之间反复横跳**
- 位置：左侧表单「月总 token 量」输入框及其下方辅助文案、右侧结果卡片算式、底部「计算公式」卡片
- 现象：输入框标签写「月总 token 量（万）」，框内默认值 `4000`；可下方辅助文案立刻变成「输入 10M / 输出 30M tokens（月总量 40M）」，结果卡片算式又用「× ¥12/M」，底部公式卡再注释「『总token』单位为百万 token（M）」。用户刚在输入框填了 4000（万），转头就要在脑子里把 4000 万 ÷100 换算成 40M，页面没有任何「1 万 = 0.01M」之类的换算锚点。
- 建议：统一对外单位。要么输入框直接以「百万 token（M）」为单位（默认 40，加后缀 M），要么在输入框内加后缀「万」并在结果区同时标注「= 40M tokens」，避免两套单位无提示切换。

### 2. **[P1] 模型选择分段按钮换行凌乱，出现「孤行按钮」**
- 位置：左侧卡片顶部「选择模型」按钮组
- 现象：8 个模型按钮 `flexWrap: wrap`、`padding: 6px 16px`，桌面视口下第一行挤进 7 个按钮，`Claude Sonnet 4.5` 孤零零折到第二行，右侧留下大片空白；移动端卡片最小宽度 320px 时会折成 3–4 行，按钮块高低不齐，垂直空间被大量占用。
- 建议：改为固定两行网格（如 `grid-template-columns: repeat(2, 1fr)`）或让按钮组等宽撑满（`flex: 1` 均分），避免任意换行产生孤行；移动端可考虑改为下拉 Select。

### 3. **[P1] 结果卡片固定 `width:400`，在手机上横向溢出**
- 位置：右侧蓝色结果卡片
- 现象：源码为 `width: 400, flex: "1 1 280px"`。在 375px 手机视口下，页面左右 padding 16px 后可用宽度约 343px，而卡片写死 400px，flex-wrap 换到第二行后仍按 400px 渲染，必然产生横向滚动条/右侧内容被裁切。
- 建议：去掉固定 `width: 400`，改为 `flex: 1 1 100%`（移动端全宽堆叠）+ 桌面 `flex-basis: 400px`，并用媒体查询控制；加 `min-width: 0` 防溢出。

### 4. **[P1] 算式明细里缓存命中率显示成小数 `(1 − 0.3)`，与 UI 的「30%」对不上**
- 位置：右侧蓝色结果卡片算式行
- 现象：缓存命中率按钮显示「0% / 30% / 60%」，但下方算式渲染成「输入 10M × ¥12/M × (1 − 0.3) ≈ ¥84」——按钮选 30%，公式里却突然变成 0.3，百分号与小数两种表示混用，用户无法心算核对这笔账。
- 建议：算式统一用与按钮一致的口径，写成 `(1 − 30%)`，或在算式下方补一行「缓存命中率 30%（折减输入成本）」让两者显式对应。

### 5. **[P1] 同一卡片内数字千分位格式不统一**
- 位置：右侧蓝色结果卡片
- 现象：大金额 `¥{Math.round(result).toLocaleString()}` 输出「¥1,884」带千分位；但算式明细用 `toFixed(0)` 输出「≈¥1800」「≈¥84」，「1800」没有千分位，一旦总量放大（如月成本 ¥180,000），明细会连成「180000」一串，与标题的千分位风格割裂。
- 建议：所有金额统一走同一个格式化函数（`Number(n).toLocaleString('zh-CN', {maximumFractionDigits: 0})`），保证标题、明细、同预算推荐三处千分位一致。

### 6. **[P1] 「同预算可考虑」名不副实，且不可点击**
- 位置：右侧蓝色卡片底部「同预算可考虑」
- 现象：源码 `others = UI_MODELS.filter(m => m.id !== modelId).slice(0, 2)`，只是固定取模型列表里排第 2、3 位的两个模型（Claude Opus 4.5、Gemini 3 Pro），与「同预算」「更便宜」无关——即使 DeepSeek-R1 便宜得多也不会出现；且渲染为纯文本 `div`，无链接、不可点击、不能加入对比，用户看到名字却无法操作。
- 建议：要么按当前预算从全部 8 个模型里真正挑出「成本最接近 / 最低」的 2–3 个；要么改名「其他模型同用量成本」；同时把每条做成可点链接（跳转详情或一键加入对比）。

### 7. **[P2] 月 token 输入框无单位后缀、无千分位、清空时静默归零**
- 位置：左侧卡片「月总 token 量（万）」Arco `InputNumber`
- 现象：输入框 `width: 200` 写死，框内只有纯数字 `4000`，单位「万」只出现在 label 括号里；输入大数字如 `1000000` 时数字紧贴左侧、无千分位分隔，难以快速判断量级；`onChange` 在非数字时 `setTotalWan(0)`，用户清空输入框后结果直接变成 ¥0，没有「请输入有效用量」之类的提示。
- 建议：给输入框加后缀「万 tokens」（Arco `addAfter`）；输入展示层加千分位；为空时显示占位态（结果区置灰「—」）而非静默 ¥0。

### 8. **[P2] 两个分段控制器视觉语言不一致**
- 位置：「选择模型」按钮组 vs「缓存命中率」按钮组
- 现象：模型选择组是 `display:flex; flexWrap:wrap` 占满整行；缓存命中率组却是 `display:inline-flex` 收缩在左侧。同样是分段选择器，一个撑满、一个靠左，圆角、内边距虽相同，但对齐方式不一致，看起来像两套组件。
- 建议：统一为同一种 segmented-control 样式；若模型组需要换行，缓存组也应对齐到同一视觉基线（或两者都改为等宽撑满）。

### 9. **[P1] 表单 label 未与控件关联，滑块/按钮组缺无障碍语义**
- 位置：左侧整个表单
- 现象：所有字段标题都是裸 `<div>`（「月总 token 量（万）」「输入占比 α…」「缓存命中率」），没有 `<label htmlFor>`；`<input type="range">` 无 `aria-label`/`aria-valuetext`，屏幕阅读器只会朗读「滑块 0.25」；模型/缓存按钮组是一排 `<button>`，没有 `role="radiogroup"` 或 `aria-pressed`，读屏用户无法知道这是单选。
- 建议：字段标题包 `<label>` 并 `htmlFor` 指向控件 id；range 加 `aria-label="输入占比 α"` 与 `aria-valuetext`；按钮组加 `role="radiogroup"`、每个按钮 `aria-pressed={active}`。

### 10. **[P2] 结果数字切换时瞬间跳变，无任何过渡反馈**
- 位置：右侧蓝色卡片大金额「¥1,884」
- 现象：切换模型或拖动 α 滑块时，金额、算式、同预算推荐全部瞬间重绘，大数字从 ¥1,884 直接跳到 ¥2,355，没有数字滚动/淡入过渡，用户视线难以锚定「哪个数字变了」。
- 建议：给金额加 150–250ms 的数字滚动（count-up）或 opacity 过渡，让变化可感知。

### 11. **[P2] 货币符号直接用 ¥，无币种说明/切换**
- 位置：全页所有金额
- 现象：GPT-5、Claude、Gemini 等均为海外模型，页面却直接以「¥」（人民币）标价，没有任何「按人民币估算 / 汇率口径 / 可切美元」说明，用户无法确认价格口径来源。
- 建议：在「价格更新于 2026-10-12」旁补一行「价格已按 ¥/1M tokens 口径折算」，或提供 USD/CNY 切换；至少在方法论里说明币种假设。

## 二、评分方法论（/methodology）

### 12. **[P0] 整页横向 padding 写死 44px，不随屏宽响应**
- 位置：面包屑、标题区、主体容器
- 现象：源码面包屑 `padding:"14px 44px 0 44px"`、标题 `padding:"24px 44px 0 44px"`、主体 `margin:"18px 44px 0 44px"` 全部硬编码 44px，**没有**用全站已有的 `.mr-pad-x`/`.mr-mx`（移动端 16px、桌面 44px）。手机上左右各留 44px 白边，正文被挤到屏幕中央一条，且与成本计算器页面（用了 mr-pad-x，移动端 16px）横向间距不一致。
- 建议：全部改用 `.mr-pad-x` / `.mr-mx` 工具类，与全站其余页面对齐。

### 13. **[P0] 右侧栏 `width:360 flex:none` 无 flexWrap，移动端两栏不堆叠**
- 位置：主体 `display:flex; gap:20` 下的右侧栏（口径假设/更新日志/按钮组）
- 现象：左栏 `flex:1`、右栏 `width:360 flex:none`，容器没有 `flexWrap:wrap`。在 375px 手机上，右栏固定占 360px，左栏 flex 被压到几乎为 0（375 − 360 − 20 gap < 0），正文直接溢出或被挤成极窄一列，卡片根本不会上下堆叠。
- 建议：容器加 `flexWrap: wrap`，右栏移动端 `flex: 1 1 100%`、桌面 `flex: 0 0 360px`；与成本计算器的 flex-wrap 堆叠逻辑保持一致。

### 14. **[P1] 「导出快照（占位）」占位文案直接外露给用户**
- 位置：右侧栏底部第二个按钮
- 现象：按钮文案为「导出快照（占位）」，未完成功能的开发占位文字直接出现在生产 UI 上，严重破坏专业感与可信度。
- 建议：功能未就绪时隐藏按钮，或改为禁用态「导出快照（即将上线）」并加 `disabled`；上线前删掉「（占位）」字样。

### 15. **[P1] 「对结果有异议？申诉 →」是无任何行为的死按钮**
- 位置：右侧栏底部第一个 `mr-btn-outline` 按钮
- 现象：`<button className="mr-btn-outline">对结果有异议？申诉 →</button>` 没有 `onClick`、没有 `href`，点击后毫无反应，用户被「→」引导却落空。
- 建议：至少链到 `/disclaimer` 或一个申诉表单 `mailto:`；未做之前先隐藏，不要放一个看似可点的死按钮。

### 16. **[P1] 数据源清单表格无表头，污染风险无视觉分级**
- 位置：「数据源清单」卡片内五行 flex 列表
- 现象：五行数据用 `display:flex` 三列排布（基准名 / 权重 xx% / 污染风险 高），**没有列标题行**，用户要靠猜才知道右边两列是「权重」和「污染风险」；污染风险只有「高/中/低」纯文字，全站明明定义了 `--mr-down`/`--mr-warn` 等警示色却完全没用——LMSYS Chatbot Arena 权重高达 35% 且污染风险「高」，却和低风险项一样灰扑扑一行，毫无警示。
- 建议：加一行表头（基准 / 权重 / 污染风险）；污染风险用 badge 着色：高=红/橙底、中=黄底、低=绿底，让高权重+高风险项一眼可辨。

### 17. **[P1] 两套权重体系并列出现，却没有建立映射关系**
- 位置：「综合分权重公式」卡片 vs「数据源清单」卡片
- 现象：上方公式是**维度权重**（综合分 = 0.35×推理 + 0.25×代码 + 0.20×数学 + 0.12×中文 + 0.08×多模态）；下方数据源清单是**基准权重**（LMSYS 35% / GPQA 20% / LiveBench 20% / SWE-bench 15% / C-Eval 10%）。两套数字加起来都是 100%，但页面完全没说明「哪个基准归入哪个维度」（如 GPQA→数学、SWE-bench→代码、C-Eval→中文），读者无法判断综合分到底按哪套权重计算。
- 建议：在数据源表格里加一列「对应维度」，或在公式卡片下补一句「基准→维度映射：LMSYS→推理、GPQA→数学……」，把两套权重的关系讲透。

### 18. **[P2] 长文缺少章节锚点导航（TOC）**
- 位置：整页内容区
- 现象：方法论是多章节长文（权重公式 / 归一化映射 / 数据源清单 / 口径假设 / 更新日志），但没有右侧目录锚点、没有 scroll-spy；右侧栏放的是「口径假设/更新日志」而非章节导航，长文阅读无法快速跳转。
- 建议：右侧栏（或桌面端悬浮目录）做 sticky TOC，列出各章节标题并锚点跳转，当前章节高亮。

### 19. **[P2] 正文行宽过长，无 max-width 约束**
- 位置：「归一化映射」「口径假设」等正文段落
- 现象：宽屏（1440px）下左栏正文卡片宽近 900px，13px 中文一行排到 60+ 字，远超中文舒适行宽（约 40–50 字/行），长段落换行后阅读回扫吃力。
- 建议：正文文本块加 `max-width: 65ch` 或约 700px 居中，公式/表格可通栏，正文收窄。

### 20. **[P2] 更新日志日期缺年份，格式与全站不一致**
- 位置：右侧栏「更新日志」
- 现象：日期写成 `10-16`、`10-12`、`10-08`，只有月-日、没有年份；而成本计算器结果卡片写的是完整「价格更新于 2026-10-12」。跨年之后读者无法判断这些条目是哪一年的。
- 建议：统一为 `2026-10-16` 完整日期格式，或至少今年用「10-16」、跨年条目补年份。

### 21. **[P2] 符号 α 在两个页面含义冲突**
- 位置：方法论「综合分权重公式」说明行 vs 成本计算器「输入占比 α」
- 现象：成本计算器里 α = 输入 token 占比（默认 0.25）；方法论里却写「α = 0.25 指数平滑周环比」。同一个希腊字母 α 在站内两个页面代表完全不同的东西，用户刚从计算器过来极易混淆。
- 建议：两处改名区分——成本计算器用「输入占比 r」或直接写「输入占比」，方法论把平滑系数改叫「β」或「平滑系数 α_s」，并在方法论首次出现时注明「此处 α 与成本计算器的输入占比无关」。

### 22. **[P2] 辅助说明文字对比度低于 WCAG AA**
- 位置：两页所有 `--mr-text-3`（#86909c）12px 辅助文案
- 现象：`--mr-text-3: #86909c` 在白底 `#f2f2f7`/卡片 `#fff` 上对比度约 3.3–3.6:1，低于 WCAG AA 对正文级文字要求的 4.5:1；深色模式下该色值仍是 #86909c，在 `#0f172a` 深底上同样偏低。「步进 ±100 万 token」「默认 30%」这类帮助文案会显得发虚。
- 建议：把 `--mr-text-3` 在浅色模式加深到约 #6b7280（≥4.5:1），深色模式提亮到 #9aa4b2；或把 12px 帮助文案升到 13px 并改用 `--mr-text-2`。
